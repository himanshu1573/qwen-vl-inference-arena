Final config: `max_num_seqs=256`, `max_num_batched_tokens=4096`, compiled mode (CUDA graphs),
`--api-server-count 2`, prefix caching and chunked prefill on (defaults), 300 users.
Exact commands: `submission/final_command.sh`. JSON: `submission/final_result.json`.
The same config scored 4.41B in an earlier run (`m-compiled-api2`), 6% apart.

Reference (internal dry run, 2 GPUs, Modal, client on a laptop): ≈ 3.3M. **Not directly
comparable**: our load tester ran on the GPU box itself, so TTFT has no internet RTT in it.
Our own default-config baseline on the same setup was 6.6M (seq32, 50 users).

## Method

1. Read the scorer first. Users is a configured multiplier, so until latency bends the score
   grows roughly as users² / (TTFT × ITL). The first job is finding the user count where p95 bends.
2. Ran vLLM and the load tester on one rented H100 (`tools/runpod_matrix.sh`), so every run used
   the same client, network path and GPU. vLLM restarts only when server knobs change.
3. Changed one knob at a time. Wrote the hypothesis before each run (`EXPERIMENTS.md`).
4. When a result was surprising, looked at `top` during the load phase to find which process was
   the wall, then changed the knob that relieves that process.
5. Repeated the baseline to measure noise, then re-ran the winner as the final submission.

## Best configuration and why it won

Each step removed the current wall, and the next wall became visible:

1. **Admission queue → `max_num_seqs` 256.** With 32 seats, 100 users gave +14% throughput
   and 5× TTFT while ITL stayed flat: requests were waiting, not computing. Decode of a 4B model
   is memory-bound, so a batch of 128–256 costs only a few ms more per step than 32
   (ITL 20.8 → 25 ms). Score at 100 users: 3.1M → 121M.
2. **EngineCore CPU → CUDA graphs.** At 300 users the RunPod dashboard showed ~40% GPU
   utilization and `top` showed `VLLM::EngineCore` pinned at 100% of one core. ITL was ~25 ms at
   any batch size: fixed per-step overhead from launching kernels one by one in eager mode.
   Compiled mode replays the step as a graph: ITL 25 → 8.5 ms, throughput +43%.
3. **API server CPU → `--api-server-count 2`.** Compiled mode alone raised TTFT to 832 ms.
   `top` now showed the single API server process (HTTP, tokenization, image preprocessing,
   streaming 12k chunks/s) pinned at 100%. Two API server processes ran at 82% and 72%, TTFT
   fell to 127 ms, and ITL held at 8.7 ms. `nvidia-smi` in the recorded final run showed 87% GPU
   utilization at 536 W (one sample), against ~40% on the dashboard for eager mode.

## Which optimization helped the most

`max_num_seqs`: 39× at the same 100 users (3.1M → 121M), and it is what let the user count
reach 300. Compiled mode + 2 API servers together gave the next 5.8× (802M → 4.68B), but only
together: compiled mode alone lowered the score.

## Which optimization failed or surprised us

- **Compiled mode alone was a net loss** (600M → 533M) despite 3× better ITL. Faster decode meant
  each user came back sooner (86 → 145 req/s), and the single API server could not keep up.
- **Wrong hypothesis:** I expected compiled TTFT to come from prefills queueing behind the 4096
  token budget. Raising it to 8192 made TTFT worse (962 ms). `top`, not the budget, found the cause.
- **Prefix caching, chunked prefill, b2048 and b8192 showed no measurable effect.** The same
  baseline config scored 600M and 802M 30 minutes apart (ITL 24.9 vs 20.8 ms) on a shared host
  whose load average was 50–70. Everything within ~30% is noise here; only the 5–40× changes count.

## Limitations

- **The final run is limited by the load generator.** At 16k chunks/s the single-process Python
  client was at ~99% CPU. Measured TTFT includes client-side delay, and the server's capacity is
  higher than reported. The user knee for the final config was not searched (all compiled runs
  used 300 users).
- Single runs, apart from the two repeats and the final re-run.
- Different platform and client placement from the Modal reference, as noted above.
- Cost: about 80 minutes of H100 time at $4.00/hr, about $5.50 including setup.

## What we would try next with more time

- A multi-process load generator, so the client stops being the wall, then a user sweep
  (300 → 600) and `--api-server-count` 3–4 on the final config.
- Three repeats per toggle run to rank prefix caching, chunked prefill and batch tokens.
- The text track with the same chain of fixes.
- Split routing: send `long` and `image` requests to a replica tuned for prefill and `text` to
  one tuned for decode, so one class's p95 stops setting the other's.
- FP8 KV cache or weights, validated against the quality pass rate before use.
